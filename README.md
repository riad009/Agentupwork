# Upwork AI Job Hunter

A production-ready SaaS that helps one freelancer spend their Connects on the jobs they can actually win.

Every few hours it discovers Upwork jobs through the **official API**, scores each one honestly, ranks and shortlists
the best, writes a proposal grounded in the freelancer's real portfolio, and — for the rare exceptional opportunity —
generates, deploys and screenshots a small concept demo plus a designed client brief.

Then it stops. **Nothing is submitted and no Connects are spent until the user explicitly approves an individual
proposal and confirms its cost.**

---

## Safety position

This product is decision support, not proposal spam. It deliberately does **not**:

- scrape Upwork or drive it with browser automation
- bypass any Upwork restriction or rate limit
- mass-submit proposals
- spend Connects without an explicit, per-proposal confirmation
- contact clients outside permitted Upwork workflows
- claim capabilities the official API does not have

It **does** automatically discover, score, filter, rank, write proposals, build and deploy demos, generate briefs and
notify the user. The final submission is always a human decision.

When the official API cannot do something — file attachments on a proposal are the concrete case — the UI says so and
offers the supported manual workflow instead of working around it.

## Architecture

```
src/
  app/                     Next.js App Router — pages, layouts and API routes
    (auth)/                Login, register, forgot/reset password
    (app)/                 Authenticated product surface
    api/                   REST endpoints, all authenticated and validated
  components/
    ui/                    shadcn/ui primitives
    layout/                App shell, sidebar, user menu
    charts/                Recharts wrappers
    shared/                Stat cards, empty/error states, pagination, skeletons
    <feature>/             Feature-specific client components
  features/                Business logic, isolated from transport and UI
    pipeline/              The end-to-end automation run
    jobs/                  Ranking engine and job queries
    proposals/             Generation, regeneration, submission
    demo/                  Demo build orchestration
    analytics/ admin/ automation/
  lib/                     env, prisma, auth, crypto, logging, rate limiting, errors
  services/                External integrations behind replaceable interfaces
    upwork/                Official API client + provider interface + sample provider
    claude/                Anthropic client with forced structured output
    github/ vercel/ email/ pdf/ screenshots/ browser/ templates/ demo/
  workers/                 BullMQ queues, worker process, scheduler
  prompts/                 Every Claude prompt, versioned as code
  schemas/                 Zod validation for input and AI output
  types/                   Shared domain types
prisma/                    Schema, migration and seed
```

**Integrations are isolated.** `services/upwork` exposes a `UpworkProvider` interface with two implementations (the
official API client and a sample-data provider); nothing outside that folder knows which is in use. GitHub, Vercel,
email and Claude follow the same pattern, so a provider can be swapped without touching the pipeline.

### The pipeline

```
Official Upwork API
  → discover up to 100 jobs across every active search profile
  → de-duplicate against jobs already stored for this user
  → score each job with Claude (skill, client, competition, budget, risk, win probability)
  → blend model scores with hard marketplace signals and rank
  → select the top N (5 / 10 / 20, configurable)
  → extract structured requirements
  → compute a demo value score
  → for exceptional opportunities only: plan → generate → validate → publish → deploy → verify → screenshot
  → write the proposal, inserting the verified demo URL naturally
  → render the designed client brief PDF
  → save everything as PENDING APPROVAL
  → email the user
──────────────────────────────────────────────────────────────
  user reviews → user approves → Connects confirmation dialog → official API submission
```

### Demo philosophy

A demo exists to prove understanding, not to build the client's product for free. Each one is:

- **3–7 screens maximum**, frontend-only, mock data, no real backend or integrations
- generated by **modifying a reusable template** (ten industry templates ship in `services/templates`) rather than
  writing an app from zero — this is the single biggest token saving in the system
- built from a **fixed, known-good scaffold**; the model only writes page bodies, against a documented component kit
  and a strict import allow-list
- honest: nothing pretends a payment processed, an email sent or a model ran, and every demo carries a
  **Demo Coverage** page mapping the client's own requirements to what the prototype shows, plus what production
  delivery would add

Generation is gated so resources go where they change the outcome:

| Job score | Behaviour |
| --- | --- |
| 90–100 | May automatically build a demo (subject to the demo value gate) |
| 80–89 | Proposal and brief; demo only when the value score clears the threshold |
| 70–79 | Proposal and brief only |
| Below 70 | Proposal only — no requirements extraction, brief or demo |

Every threshold and every hard limit (`maxDemoPages`, `maxDemoIterations`, `maxBuildFixAttempts`, `maxScreenshots`,
`maxDemosPerRun`) is configurable per user under **Settings → Automation**.

## Getting started

```bash
npm install
cp .env.example .env          # then fill in DATABASE_URL, AUTH_SECRET and ENCRYPTION_KEY at minimum
npx prisma generate
npx prisma migrate deploy     # or `npm run db:migrate` in development
npm run db:seed               # optional: admin account, search profiles, portfolio
npm run dev
```

In a second terminal, for scheduled and queued runs:

```bash
npm run worker
```

Generate the two required secrets with:

```bash
openssl rand -base64 32   # AUTH_SECRET
openssl rand -hex 32      # ENCRYPTION_KEY
```

With `UPWORK_PROVIDER="mock"` (the default) the whole pipeline is exercisable without Upwork credentials. The sample
provider returns fixture jobs, never contacts Upwork, and **cannot submit a proposal**.

## Integrations

| Integration | Purpose | Required for |
| --- | --- | --- |
| **Upwork** (OAuth2 + GraphQL) | Job discovery, Connects balance, proposal submission | Real jobs and submission |
| **Claude** | Scoring, requirements, proposals, demo planning and code, client brief | Everything AI |
| **GitHub** | Publishes each demo to its own repository | Demo repositories |
| **Vercel** | Deploys demos and reports build status | Live demo URLs |
| **Resend / SMTP** | Proposal alerts, run failures, password resets | Email |

Each one can be configured per user in **Settings**, or platform-wide through environment variables. Per-user
credentials take precedence. Every stored secret is encrypted with AES-256-GCM and is only ever decrypted server-side,
at the moment of use — no secret is ever returned to the browser, in any response, in any form.

## Security

- **Encryption at rest**: Upwork tokens and all integration secrets use AES-256-GCM with a versioned payload format.
- **Authentication**: Auth.js (NextAuth v5) with a credentials provider, bcrypt at cost 12, JWT sessions, and secure
  `httpOnly` cookies. Auth checks run in middleware (edge-safe config) and again in every page and route handler.
- **Authorization**: every query is scoped by `userId`; roles are `USER` and `ADMIN`. Admin views expose aggregates
  only, never user secrets.
- **Input validation**: Zod on every request body and query string — and on every Claude response, which is forced
  through tool-use so a malformed structure fails validation rather than silently entering the database.
- **Rate limiting**: Redis-backed fixed window with an in-process fallback, applied to registration, password reset,
  submissions, regeneration, demo rebuilds and manual runs.
- **CSRF**: Auth.js CSRF tokens on auth routes; mutations are JSON-only `POST`/`PATCH`/`PUT`/`DELETE` with
  `SameSite=Lax` cookies.
- **Webhooks**: HMAC-SHA256 signature verification, constant-time comparison; unsigned requests are rejected.
- **Audit logging**: connection changes, submissions and auth events are recorded with secrets scrubbed.
- **Structured logging**: pino with redaction of tokens, cookies and passwords.
- **Error monitoring**: dependency-free Sentry envelope transport, enabled by setting `SENTRY_DSN`.
- **Database**: indexes on every filter and sort path; `@@unique([userId, upworkJobId])` prevents duplicate jobs.
- **Retries**: exponential backoff with jitter on every outbound integration call.

Secrets that never reach the browser: `UPWORK_CLIENT_SECRET`, `ANTHROPIC_API_KEY`, `VERCEL_TOKEN`, `GITHUB_TOKEN`,
`DATABASE_URL`, `AUTH_SECRET`, `ENCRYPTION_KEY`, `RESEND_API_KEY`, `SMTP_PASSWORD`.

## Failure handling

Each stage degrades independently rather than failing the run:

| Failure | Behaviour |
| --- | --- |
| Claude analysis fails | Retried with backoff; on exhaustion the job is skipped and logged, the run continues |
| Demo generation fails | The proposal is still prepared and saved, without a demo link |
| Vercel deployment fails | Build logs feed a bounded repair loop; if it still fails, no URL is inserted anywhere |
| Deployment renders an error | Verified before use — a broken deployment is treated as no demo |
| Screenshots or PDF unavailable | Proposal and demo are unaffected; the document is marked `FAILED` with the reason |
| Upwork submission fails | Status becomes `FAILED` with the API's own error shown, and **no Connects are spent** |
| Redis unavailable | Runs execute in-process; the UI says which path was taken |

**Idempotency**: each proposal carries a stable `idempotencyKey` that is the unique key of its `Submission` row. A
double click, a retried request or two concurrent submissions cannot produce two submissions — the second is rejected
at the database level. The submit endpoint also requires the client to echo back the exact Connects figure it
displayed, so a stale dialog can never authorise an unexpected cost.

## Deployment notes

- The web app runs anywhere Next.js does. The worker (`npm run worker`) is a separate long-running process.
- Demo generation writes to `STORAGE_DIR` (screenshots, PDFs) — mount persistent storage, or point it at object
  storage-backed volumes.
- Set `VERCEL_WEBHOOK_SECRET` before pointing Vercel deployment webhooks at `/api/webhooks/vercel`; the endpoint
  rejects everything until it is configured.
- `/api/health` reports database and Redis connectivity for your orchestrator.
